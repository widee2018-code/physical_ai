# OccuCool 사람 검출 모델 선정 및 학습·검증 계획

검토 자료: `PRD/PRD_AI.md`(제품 요구사항), `report/model_selection.md`(작성 요구 항목), `report/preprocess_report.md`·`report/postprocess_report.md`(전·후처리 설계안), `code/occucool_pipeline/occucool/vision.py`(현재 검출기 코드)
학습 장비: MacBook Air M4 (CPU 10코어, 통합 메모리 16GB, 팬 없음)
배포 장비: NXP i.MX 8M Plus (NPU 2.3 TOPS), TFLite INT8

> 표시 규칙: **(가정)**은 아직 실측하지 않은 값입니다. 파일럿·벤치마크 결과로 바꿔야 합니다.

## 0. 요약

| 항목 | 결정 |
|---|---|
| 모델 | **YOLO11n** (1순위). NPU 호환성 문제가 생기면 **YOLOv8n**으로 바꿉니다. YOLO26n은 비교 후보로 둡니다. |
| 입력 해상도 | 학습은 **416**, 배포는 **320과 416을 실기기에서 비교한 뒤** 결정합니다. |
| 클래스 | `head`(머리, 인원 계수용)와 `person`(보이는 몸 전체, 구역 할당·교차 검증용) 2개 |
| 전이학습 | COCO 사전학습 가중치 → 공개 데이터(머리·천장 시점)로 1차 학습 → 자체 천장 데이터로 2차 학습 |
| 학습 전략 | **2단계**: 1단계는 백본을 고정(`freeze=11`)하고 헤드만 학습, 2단계는 전체를 풀고 낮은 학습률로 학습 |
| 맥북 최적화 | `device='mps'`, FP32, `batch=16`, `cache='disk'`, `multi_scale=False`, 발열 관리, 체크포인트 저장 |
| 증강 초기값 | `scale=0.5`, `mosaic=1.0`(마지막 10 epoch 끔), `multi_scale=False`, `flipud=0.5`, `fliplr=0.5` |
| 하이퍼파라미터 | `optimizer='AdamW'`(명시), `lr0=0.001`→`0.0002`, `epochs=50+100`, `patience=15/25`, `cos_lr=True` |
| 합격 기준 | mAP가 아니라 **인원 계수 지표**로 판정합니다. ±1명 이내 95% 이상, MAE 0.5명 이하, 공실 오검출률 1% 이하, INT8 추론 200ms 이하 |

이 문서는 두 질문에 답합니다.

1. **OccuCool에 맞는 모델은 무엇인가** (1~2장)
2. **어떻게 학습하고 어떻게 검증하는가** (3~9장)

## 1. 문제를 모델 요구사항으로 바꾸기

모델을 고르기 전에 PRD 문장을 측정할 수 있는 요구사항으로 바꿨습니다.

| PRD 요구 | 모델 요구사항 | 모델 선택에 주는 영향 |
|---|---|---|
| 착석·정지, 부분 가림, 다양한 조명에서 인원 계수 | 책상에 가려 머리만 보이는 사람도 검출해야 합니다 | 몸 전체가 아니라 **머리 검출**을 주 클래스로 둡니다 |
| ±1명 이내 95%, MAE 0.5명 (0~15명) | 검출 지표(mAP)보다 **이미지당 개수 오차**가 중요합니다 | 평가를 카운트 지표 중심으로 설계합니다 (7장) |
| 재실 중 절전 오작동 월 1건 이하 | 미검출(FN)이 오검출(FP)보다 위험합니다 | 재현율을 우선하고, 낮은 conf 검출은 추적기로 넘깁니다 |
| 5fps 이상, 지연 200ms 이하, i.MX 8M Plus NPU | INT8로 양자화해 NPU에서 돌아가야 합니다 | **nano급**, NPU에서 지원되는 연산 위주의 구조가 필요합니다 |
| 모델 크기 5~10MB | 파라미터 약 1천만 개 이하(INT8 기준) | n 또는 s 크기만 후보가 됩니다 |
| 천장 2.4~3.5m, 광각 110~130°, 저조도 IR | 위에서 내려다본 시점, 화면 가장자리의 왜곡, 흑백 IR 영상 | COCO 사전학습만으로는 부족하므로 **천장 시점 데이터로 미세조정**합니다 |
| 영상 저장·외부 전송 0건 | 제품에서는 학습 데이터를 모을 수 없습니다 | 동의를 받은 **별도 데이터 수집 세션**이 필요합니다 (4장) |

### 1-1. 왜 머리(head) 검출인가

천장 시점에서 사람 수를 셀 때는 머리가 가장 안정적인 단서입니다.

- **착석 상태**: 책상과 의자가 몸통과 다리를 가리지만, 머리와 어깨는 위에서 거의 항상 보입니다.
- **밀집 상황**: 회의실에 11명 이상이 모이면 몸 박스는 서로 크게 겹쳐 NMS가 사람을 지워 버립니다. 머리 박스는 잘 겹치지 않습니다.
- **박스 정의**: 위에서 본 사람의 "몸 전체 박스"는 자세에 따라 모양이 크게 달라져 라벨 기준이 흔들립니다. 머리는 크기와 모양이 일정합니다.

다만 머리는 작습니다. 천장 2.4m, 시야각 120°, 입력 320px이면 화면 가장자리의 머리가 **약 10~20px**까지 작아집니다 (가정, 실측 필요). 그래서 학습 해상도를 416으로 올리고, 배포 해상도는 실측으로 정합니다.

`person` 클래스도 함께 학습합니다. 이유는 두 가지입니다.

- 전처리 설계안 V6(바닥 평면 투영)은 **발 위치**(박스 하단 중앙)를 씁니다. 이 값은 몸 박스가 있어야 계산할 수 있습니다.
- 머리가 가려진 경우(모자, 후드, 화면 가장자리) 몸 박스로 보완할 수 있습니다.

클래스를 하나 더 추가해도 검출 헤드의 출력 채널만 1개 늘어나므로 연산량 차이는 거의 없습니다.

## 2. YOLO 모델 중 적합한 모델 (모델 크기)

### 2-1. 후보 비교

COCO val 기준 공개 수치이며, 640 입력 기준입니다. 연산량은 입력 크기의 제곱에 비례하므로 416 입력이면 약 0.42배, 320 입력이면 약 0.25배가 됩니다.

| 모델 | 파라미터 | GFLOPs @640 | GFLOPs @416 (환산) | COCO mAP50-95 | INT8 크기 (추정) | 판단 |
|---|---|---|---|---|---|---|
| YOLOv8n | 3.2M | 8.7 | 약 3.7 | 37.3 | 약 3.5MB | NPU 호환성이 가장 검증됨. **대안** |
| **YOLO11n** | 2.6M | 6.5 | 약 2.7 | 39.5 | 약 3MB | 더 적은 연산으로 더 높은 정확도. **1순위** |
| YOLO26n | 약 2.4M | 약 5.4 | 약 2.3 | 약 40 | 약 3MB | NMS가 필요 없는 구조로 엣지에 유리. 도구 지원이 안정되면 비교 |
| YOLO11s | 9.4M | 21.5 | 약 9.1 | 47.0 | 약 10MB | 크기 상한에 걸림. **정확도 상한 확인용**으로만 학습 |
| YOLOv8s | 11.2M | 28.6 | 약 12.1 | 44.9 | 약 11MB | 크기 상한 초과. 제외 |
| m 이상 | 20M 이상 | 68 이상 | - | 50 이상 | 20MB 이상 | NPU 예산과 크기 상한 초과. 제외 |

> YOLO26 수치는 공개 자료 기준의 근사값입니다. 사용 시점의 Ultralytics 문서에서 다시 확인해야 합니다.

### 2-2. YOLO11n을 고른 이유

1. **연산 예산이 넉넉합니다.** 5fps이면 프레임당 200ms를 쓸 수 있습니다. YOLO11n은 416 입력에서 약 2.7 GFLOPs이므로, NPU 효율을 보수적으로 잡아도 수십 ms 안에 끝날 것으로 예상합니다 (가정). 남는 시간은 타일링(전처리 V3)과 추적기에 쓸 수 있습니다.
2. **크기 대비 정확도가 가장 좋습니다.** YOLOv8n보다 파라미터가 약 20% 적은데 COCO mAP는 2.2점 높습니다.
3. **현재 코드와 이어집니다.** `vision.py`의 `UltralyticsDetector`가 이미 `yolo11n.pt`를 기본값으로 쓰고 있어 파이프라인을 바꿀 필요가 없습니다.
4. **s 크기를 쓸 이유가 약합니다.** 이 문제는 클래스 1~2개, 시점이 고정된 단순한 검출 문제입니다. COCO 80클래스에서 생기는 n과 s의 차이는 이런 문제에서 크게 줄어듭니다. 그래도 YOLO11s를 한 번 학습해 "n이 정확도를 얼마나 손해 보는지"는 숫자로 확인합니다 (8장 실험 E2).

### 2-3. 꼭 확인해야 할 위험: NPU 연산 호환성

YOLO11은 백본 끝에 어텐션 블록(C2PSA)이 있습니다. i.MX 8M Plus NPU(VeriSilicon)의 TFLite 델리게이트가 이 블록의 일부 연산(행렬곱, Softmax 등)을 지원하지 않으면 **그 부분만 CPU로 넘어가** 지연이 크게 늘 수 있습니다.

그래서 학습을 본격적으로 하기 전에 **가중치 없이 구조만 내보내 실기기에서 먼저 재 봅니다** (실험 E0).

| 결과 | 조치 |
|---|---|
| YOLO11n INT8이 NPU에서 거의 전부 실행되고 100ms 이하 | YOLO11n 확정 |
| 어텐션 블록이 CPU로 넘어가 200ms 초과 | YOLOv8n으로 교체 (어텐션 없음, NPU 사례 많음) |
| 둘 다 INT8 정확도 하락이 큼 | SiLU를 ReLU로 바꾸거나 채널별(per-channel) 대신 텐서별(per-tensor) 양자화를 시도 (NXP eIQ 문서 확인) |

## 3. 전이학습 전략

### 3-1. 왜 처음부터 학습하지 않는가

자체 천장 데이터는 많아야 수천 장입니다 (가정). 이 정도로 처음부터 학습하면 과적합되고, 조명이나 공간이 조금만 달라져도 성능이 떨어집니다. COCO로 사전학습한 백본은 이미 가장자리, 질감, 사람 형태 같은 일반 특징을 알고 있습니다. 이 특징을 재사용하면 적은 데이터로도 일반화가 잘 됩니다.

### 3-2. 3계층 전이 경로

```
[0] COCO 사전학습 (yolo11n.pt, 80클래스)
     │  일반 시각 특징 + 'person' 개념
     ▼
[1] 공개 데이터로 도메인 적응 (head, person 2클래스)
     │  CrowdHuman, SCUT-HEAD 등 머리 라벨 + CEPDOF·HABBOF·WEPDTOF 등 천장/어안 시점
     │  → "머리"라는 새 클래스와 "위에서 본 사람"을 학습
     ▼
[2] 자체 천장 데이터로 미세조정 (OccuCool 설치 조건 그대로)
     │  2MP 광각, 2.4~3.5m, 사무실·강의실·회의실, 주간 RGB + 야간 IR
     ▼
[3] (운영) 현장별 보정·분기별 재학습   ← PRD: 클라우드 자동 학습은 범위 밖, 분기별 수동 재학습
```

| 단계 | 데이터 | 목적 | 비고 |
|---|---|---|---|
| [1] | CrowdHuman(머리·전신 박스), SCUT-HEAD(교실 머리), CEPDOF·HABBOF·WEPDTOF(천장 어안 사람) | 새 클래스 학습, 천장 시점 적응 | 각 데이터셋의 **라이선스가 상업적 사용을 허용하는지** 확인해야 합니다. 허용하지 않으면 연구·검증용으로만 씁니다. 어안 데이터의 회전 박스는 축 정렬 박스로 변환합니다. |
| [2] | 자체 수집 (4장) | 실제 설치 환경 적응 | 가장 중요합니다. 테스트셋도 이 분포에서 뽑습니다. |
| [3] | 파일럿 현장 오검출·미검출 사례 | 현장별 약점 보완 | 영상 저장이 불가하므로 동의를 받은 점검 세션에서만 수집합니다. |

`[1]`과 `[2]`를 따로 학습하지 않고 **섞어서 한 번에** 학습하는 방법도 있습니다. 시간이 부족하면 섞어서 학습하되, 자체 데이터 비율을 30% 이상 유지하고 테스트는 자체 데이터로만 합니다.

### 3-3. 클래스 헤드 처리

COCO 가중치에서 2클래스 모델을 만들면 Ultralytics가 백본과 넥 가중치는 그대로 옮기고, 클래스 수가 다른 분류 출력층만 새로 초기화합니다. 이때 **새 출력층이 무작위 값에서 시작하므로**, 처음부터 전체 학습률을 높게 주면 사전학습 특징이 망가집니다. 그래서 6장의 2단계 학습을 씁니다.

## 4. 데이터 전략 (다양한 환경 대응)

"다양한 환경에서 정확하게"는 증강만으로 얻을 수 없습니다. **실제 다양한 환경을 데이터에 넣는 것**이 먼저이고, 증강은 그 사이를 메우는 역할입니다.

### 4-1. 수집 환경 매트릭스

자체 데이터를 모을 때 아래 축을 고르게 채웁니다. 각 칸이 최소 수백 장은 되도록 합니다 (가정).

| 축 | 수준 | 왜 필요한가 |
|---|---|---|
| 공간 | 사무실, 강의실, 회의실, 로비, 카페 (5종 이상, 10개 공간 이상) | 배경과 가구 배치를 외우지 않게 합니다 |
| 천장 높이 | 2.4m, 2.7m, 3.0m, 3.5m | 머리 크기가 약 2배까지 달라집니다 |
| 설치 위치 | 천장 중앙(Top-view), 천장 모서리(사선) | 전처리 설계안에서 사선 설치가 사실상 필수라고 판단했습니다 |
| 조명 | 주간 LED, 창가 역광, 저조도, 야간 IR(흑백) | PRD의 주야간 조건 |
| 자세 | 착석, 서 있음, 걷기, 엎드려 자기 | 착석과 정지 상태가 PRD의 핵심 난제입니다 |
| 가림 | 없음, 책상·모니터, 파티션, 사람끼리 겹침 | 부분 가림 조건 |
| 인원 | 0, 1~5, 6~10, 11~15명 | PRD 제어 구간과 같습니다. **0명 이미지가 특히 중요합니다** |
| 외형 | 모자·후드, 긴 머리, 대머리, 어두운 옷, 같은 색 유니폼 | 머리 검출이 실패하기 쉬운 경우 |
| 방해 요소 | 의자에 걸린 외투, 가방, 마네킹, 사람이 나오는 모니터, 화분 | 오검출로 공실을 재실로 잘못 판단하는 원인 |

### 4-2. 수집·라벨링 원칙

- **동의와 분리**: 제품은 영상을 저장하지 않습니다. 학습 데이터는 참여자 서면 동의를 받은 **별도 수집 세션**에서만 모으고, 얼굴 식별이 안 되도록 천장 시점·저해상도로 촬영합니다. 보관 기간과 폐기 절차를 문서로 남깁니다.
- **프레임 간격**: 5fps 영상을 그대로 쓰면 거의 같은 이미지가 수천 장 생깁니다. **2~5초에 1장**만 뽑고, 사람이 움직인 장면 위주로 고릅니다.
- **라벨 기준 문서화**:
  - `head`: 머리카락과 귀를 포함한 머리 전체 박스. 50% 이상 가려지면 보이는 부분만 박스를 칩니다.
  - `person`: 보이는 몸 전체 박스.
  - 화면 경계에서 잘린 사람: 머리가 30% 이상 보이면 라벨합니다.
  - 기준을 정한 뒤 두 사람이 같은 200장을 라벨해 일치도를 확인합니다.
- **빈 방 이미지(Hard Negative)**: 전체의 **10~15%**는 사람이 없는 이미지로 채웁니다. 외투, 마네킹, 모니터 화면이 있는 장면을 우선합니다. Ultralytics는 라벨 파일이 비어 있는 이미지를 배경으로 학습합니다.
- **IR 비율**: 야간 IR 이미지를 **15~20%** 넣습니다. IR 카메라가 없으면 RGB 일부를 흑백으로 바꿔 대체하되, 테스트셋에는 반드시 실제 IR 이미지를 넣습니다.

### 4-3. 데이터 분할 (가장 흔한 실수 방지)

연속 프레임을 무작위로 나누면 학습셋과 테스트셋에 거의 같은 이미지가 들어가 점수가 부풀려집니다. 그래서 **공간(현장) 단위로 나눕니다.**

| 셋 | 비율 | 구성 |
|---|---|---|
| train | 약 70% | 공간 A~G |
| val | 약 15% | 공간 H, I (조기 종료·임계값 결정에 사용) |
| test | 약 15%, **1,000장 이상** | 공간 J, K + 야간 세션 + 0명 이미지. **학습 중 한 번도 보지 않습니다** |

test는 PRD 요구대로 **1,000장 이상**, 0~15명, 주야간, 부분 가림을 모두 포함해야 합니다.

### 4-4. 데이터 증강 초기 전략 (scale, mosaic, multi_scale)

| 파라미터 | 초기값 | 조정 범위 | 이유 |
|---|---|---|---|
| `scale` | **0.5** | 0.3~0.6 | 천장 2.4~3.5m에서 머리 크기가 약 2배까지 달라집니다. 0.5는 0.5~1.5배 범위를 만들어 이 변화를 덮습니다. 1단계 결과에서 작은 머리 재현율이 낮으면 0.6으로 올립니다. |
| `mosaic` | **1.0** | 1.0 / 0.5 | 4장을 합쳐 한 장에 사람 수와 배경 종류를 늘립니다. 데이터가 적은 이 프로젝트에 효과가 큽니다. 다만 실제와 다른 장면을 만들므로 `close_mosaic=10`으로 **마지막 10 epoch는 끕니다.** 2단계에서는 0.5로 줄입니다. |
| `close_mosaic` | **10** | 5~15 | 마지막 몇 epoch를 실제 장면 구성에 맞춰 마무리합니다. |
| `multi_scale` | **False** | False / True | 배포는 고정 해상도(INT8 320 또는 416)이므로 학습도 고정 해상도가 유리합니다. 크기 변화는 `scale`이 이미 담당합니다. 맥북 MPS에서는 배치마다 입력 크기가 바뀌면 메모리 사용이 튀고 속도가 느려집니다. 2단계에서 시간이 남으면 실험으로만 켜 봅니다. |
| `fliplr` | 0.5 | 0.5 | 좌우 대칭은 항상 성립합니다. |
| `flipud` | **0.5** | 0.0~0.5 | 위에서 내려다본 영상에는 "위아래"가 없으므로 상하 반전도 실제와 같습니다(기본값 0.0에서 바꿈). **사선 설치 데이터 비중이 30%를 넘으면 0.2 이하로 낮춥니다.** |
| `degrees` | 10 | 0~15 | 천장 시점은 회전에 강하지만, 축 정렬 박스를 회전하면 박스가 헐거워지므로 작게 둡니다. |
| `hsv_v` | 0.5 | 0.4~0.6 | 저조도와 역광 대응. 기본값 0.4보다 약간 높입니다. |
| `hsv_s`, `hsv_h` | 0.7, 0.015 | 기본값 | 조명 색온도 변화 대응 |
| `mixup`, `copy_paste` | 0.0 | 0.0 | 반투명 사람이나 붙여 넣은 사람은 계수 문제에서 오히려 혼란을 줍니다. |

## 5. MacBook Air M4 학습 하드웨어 최적화

### 5-1. 장비의 특징과 제약

| 특징 | 영향 | 대응 |
|---|---|---|
| Apple GPU (MPS 백엔드) | PyTorch가 `mps` 장치로 GPU를 씁니다. CUDA보다 느리지만 CPU보다 훨씬 빠릅니다. | `device='mps'` |
| 혼합 정밀도(AMP) 미지원 | Ultralytics는 AMP를 CUDA에서만 켭니다. MPS에서는 **FP32로 학습**하므로 메모리를 더 씁니다. | 배치와 해상도를 보수적으로 잡습니다 |
| 통합 메모리 16GB | CPU와 GPU가 메모리를 나눠 씁니다. 캐시를 RAM에 올리면 학습 메모리가 부족해질 수 있습니다. | `cache='disk'` |
| AutoBatch 미지원 | `batch=-1`(자동 배치)은 CUDA 전용입니다. | 배치를 직접 지정합니다 (`batch=16`) |
| 데이터 로딩 워커 | Ultralytics 일부 버전은 MPS에서 `workers`를 0으로 강제합니다. 그러면 mosaic 같은 증강이 메인 프로세스에서 돌아 병목이 됩니다. | 학습 로그에서 실제 `workers` 값을 확인합니다. 병목이면 `cache='disk'`로 디코딩 비용을 줄입니다. |
| 팬 없음 | 오래 학습하면 발열로 성능이 떨어집니다 (thermal throttling). | 6장의 단계를 짧게 끊고, 체크포인트를 자주 저장합니다 |
| 일부 연산 미구현 | MPS에 없는 연산이 있으면 오류가 납니다. | `PYTORCH_ENABLE_MPS_FALLBACK=1`로 CPU 대체를 허용합니다 |

### 5-3. 운영 요령

- **먼저 짧게 재 봅니다.** `fraction=0.1`, `epochs=3`으로 돌려 **epoch당 시간**을 잰 뒤 전체 학습 시간을 계산합니다. 이 값으로 아래 일정을 조정합니다.
- **전원과 자세**: 전원 어댑터 연결, 저전력 모드 끄기, 노트북 스탠드로 하판 통풍 확보. 덮개를 닫고 학습하지 않습니다.
- **중단 후 이어서 하기**: `model = YOLO('runs/detect/stage2/weights/last.pt'); model.train(resume=True)`
- **역할 분담**: 데이터 정리, 라벨 검수, 짧은 실험, 결과 분석은 맥북에서 합니다. **실험 수가 많아지거나 YOLO11s 비교 학습처럼 오래 걸리는 작업**은 Colab이나 클라우드 GPU로 옮기는 것이 현실적입니다. 같은 스크립트에서 `device=0`만 바꾸면 됩니다.
- **맥북 추론 속도는 참고용입니다.** 실제 지연은 반드시 i.MX 8M Plus에서 INT8 모델로 잽니다.

## 6. 하이퍼파라미터 초기 전략과 프리징·2단계 파인튜닝

### 6-1. 왜 2단계인가

| 방식 | 문제 |
|---|---|
| 전체를 처음부터 높은 학습률로 학습 | 새로 초기화된 출력층의 큰 오차가 백본까지 역전파되어 COCO에서 배운 특징이 망가집니다. 데이터가 적으면 특히 심합니다. |
| 백본을 끝까지 고정 | 안전하지만, 천장 시점·IR 같은 **낮은 수준 특징**이 COCO와 달라 성능 상한이 낮습니다. |
| **2단계 (선택)** | 1단계에서 헤드를 먼저 맞추고, 2단계에서 전체를 낮은 학습률로 조금씩 조정합니다. 안정성과 성능 상한을 모두 얻습니다. |

### 6-2. 단계별 설정

**프리징 위치**: YOLO11의 백본은 0~10번 층(마지막이 C2PSA)이므로 `freeze=11`이면 백본 전체가 고정됩니다. YOLOv8로 바꾸면 백본이 0~9번 층(마지막이 SPPF)이므로 `freeze=10`입니다.

| 파라미터 | 1단계: 백본 고정 | 2단계: 전체 미세조정 | 이유 |
|---|---|---|---|
| 시작 가중치 | `yolo11n.pt` (COCO) | 1단계 `best.pt` | |
| `freeze` | **11** | **0** (없음) | |
| `epochs` | **50** | **100** | 1단계는 학습할 파라미터가 적어 빨리 수렴합니다. |
| `patience` | **15** | **25** | 기본값 100은 너무 깁니다. 맥북에서 시간 낭비를 줄이기 위해 개선이 없으면 일찍 멈춥니다. 2단계는 낮은 학습률로 천천히 좋아지므로 더 깁니다. |
| `optimizer` | **`'AdamW'`** | **`'AdamW'`** | 기본값 `'auto'`는 **`lr0`와 `momentum`을 무시하고** 반복 횟수에 따라 자동으로 정합니다. 단계별로 학습률을 다르게 줘야 하므로 반드시 명시합니다. 데이터가 적은 미세조정에서는 AdamW가 SGD보다 수렴이 빠르고 안정적입니다. |
| `lr0` | **0.001** | **0.0002** | 2단계는 1단계의 1/5로 낮춰 사전학습 특징을 지킵니다. |
| `lrf` | 0.01 | 0.05 | 마지막 학습률 = `lr0 × lrf` |
| `cos_lr` | True | True | 끝으로 갈수록 부드럽게 줄여 수렴을 안정시킵니다. |
| `warmup_epochs` | 3 | **1** | 2단계는 이미 수렴한 가중치에서 시작하므로 짧게 둡니다. |
| `warmup_bias_lr` | 0.1 | **0.01** | 기본값 0.1은 2단계에서 학습된 bias를 흔들 수 있습니다. |
| `weight_decay` | 0.0005 | 0.0005 | 기본값 |
| `mosaic` / `close_mosaic` | 1.0 / 10 | 0.5 / 10 | 2단계는 실제 장면에 더 가깝게 학습합니다. |
| `batch`, `imgsz` | 16, 416 | 16, 416 | 5장 참고 |
| 데이터 | 공개 + 자체 혼합 | **자체 비중을 높인 혼합** (자체 50% 이상) | 2단계는 실제 설치 분포에 맞춥니다. |

> **참고**: 1단계에서 동결한 층의 BatchNorm 통계는 Ultralytics에서도 계속 갱신됩니다. 배치 16이면 문제가 거의 없지만, 배치를 8 이하로 줄였다면 1단계 결과를 다시 확인합니다.

### 6-3. 학습 스크립트

`data/occucool.yaml`

```yaml
path: /path/to/occucool_dataset
train: images/train
val: images/val
test: images/test
names:
  0: head
  1: person
```

`train_occucool.py`

```python
from ultralytics import YOLO

COMMON = dict(
    data="data/occucool.yaml",
    imgsz=416,
    batch=16,
    device="mps",
    cache="disk",
    workers=4,
    optimizer="AdamW",
    cos_lr=True,
    weight_decay=0.0005,
    # 증강 (4-4)
    scale=0.5, fliplr=0.5, flipud=0.5, degrees=10.0,
    hsv_h=0.015, hsv_s=0.7, hsv_v=0.5,
    mixup=0.0, copy_paste=0.0, multi_scale=False,
    close_mosaic=10,
    save_period=10,
    seed=0,
    project="runs/occucool",
)

# 1단계: 백본 고정, 헤드 적응
stage1 = YOLO("yolo11n.pt")
stage1.train(
    **COMMON, name="stage1_freeze",
    freeze=11, epochs=50, patience=15,
    lr0=0.001, lrf=0.01, warmup_epochs=3, mosaic=1.0,
)

# 2단계: 전체 미세조정, 낮은 학습률
stage2 = YOLO("runs/occucool/stage1_freeze/weights/best.pt")
stage2.train(
    **COMMON, name="stage2_full",
    freeze=0, epochs=100, patience=25,
    lr0=0.0002, lrf=0.05, warmup_epochs=1, warmup_bias_lr=0.01, mosaic=0.5,
)
```

> 2단계에서 데이터 비중을 바꾸려면 `occucool_stage2.yaml`을 따로 만들어 `train` 경로에 자체 데이터 목록을 더 많이 넣습니다(이미지 경로 목록 txt 사용).

### 6-4. 학습 곡선 보는 법

| 증상 | 의미 | 조치 |
|---|---|---|
| train loss는 줄고 val loss가 오름 | 과적합 | `patience`가 멈춰 줍니다. 자체 데이터를 늘리거나 2단계 `lr0`를 0.0001로 낮춥니다. |
| 1단계에서 val mAP가 금방 정체 | 백본 특징이 도메인에 안 맞음 | 정상입니다. 2단계에서 올라가야 합니다. 올라가지 않으면 `freeze`를 6 정도로 일부만 고정하는 중간안을 시험합니다. |
| 2단계 초반에 mAP가 크게 떨어짐 | 학습률이 너무 높음 | `lr0`를 절반으로 낮추고, `warmup_bias_lr`를 확인합니다. |
| `close_mosaic` 시점에 val 점수가 뜀 | 정상 | mosaic가 꺼지며 실제 장면에 적응한 결과입니다. |
| 작은 머리 재현율만 낮음 | 해상도 부족 | `scale` 0.6, 배포 해상도 416, 타일링(전처리 V3)을 검토합니다. |

## 7. 검증 전략: 무엇을 "정확하다"고 볼 것인가

### 7-1. 3단계 검증

검증은 모델 단독 → 파이프라인 → 실기기·현장 순서로 넓혀 갑니다. 앞 단계를 통과해야 다음 단계로 갑니다.

| 단계 | 대상 | 데이터 | 핵심 지표 |
|---|---|---|---|
| L1 모델 | 검출기 단독 (PyTorch, INT8) | test 1,000장 이상 | mAP50(head), Recall@운영 conf, **이미지당 카운트 MAE, ±1 정확도** |
| L2 파이프라인 | 검출 + 추적(V5) + 5초 중앙값(V7) | 라벨된 연속 영상 시퀀스 (공간별 30분 이상) | 확정 인원 MAE, 인원 변화 감지 지연 |
| L3 실기기·현장 | i.MX 8M Plus + 파일럿 현장 | 실제 운영 | 지연, 5fps 유지, 24시간 발열, 재실 중 절전 오작동 |

### 7-2. 지표 정의

mAP는 "박스를 얼마나 잘 그렸나"를 봅니다. OccuCool의 실제 목표는 "몇 명인지 맞혔나"이므로 **카운트 지표를 최종 기준**으로 씁니다.

| 지표 | 정의 | 목표 | 근거 |
|---|---|---|---|
| Count MAE | 이미지별 \|예측 인원 − 실제 인원\|의 평균 | **0.5명 이하** | PRD |
| ±1 정확도 | \|오차\| ≤ 1인 이미지 비율 | **95% 이상** | PRD |
| 정확 일치율 | 오차 0인 이미지 비율 | 참고 (80% 이상 기대) | 0↔1 경계 판단에 중요 |
| 공실 오검출률 | 0명 이미지 중 1명 이상으로 예측한 비율 | **1% 이하** (가정) | 공실인데 냉방 유지 → 절감 실패 |
| 재실 미검출률 | 1명 이상 이미지 중 0명으로 예측한 비율 | **0.5% 이하** (가정) | 재실 중 절전 오작동 → 민원. **가장 중요한 지표** |
| mAP50 (head) | IoU 0.5 기준 | 0.85 이상 (가정) | 모델 비교용 보조 지표 |
| INT8 하락폭 | FP32 대비 INT8의 mAP50·MAE 변화 | mAP50 −2%p 이내, MAE +0.1명 이내 | 양자화 검증 |
| 추론 지연 | 실기기 INT8, 전처리 포함 | **200ms 이하**, 5fps 유지 | PRD |

### 7-3. 조건별(층화) 평가

평균만 보면 약한 조건이 숨습니다. test를 아래 조건으로 나눠 **각 칸마다** 지표를 냅니다. 한 칸이라도 목표에 못 미치면 그 조건의 데이터를 보강합니다.

| 조건 | 구간 |
|---|---|
| 인원 | 0 / 1~5 / 6~10 / 11~15명 |
| 조명 | 주간 / 역광 / 저조도 / 야간 IR |
| 자세 | 착석 / 서 있음·이동 |
| 가림 | 없음 / 책상·파티션 / 사람끼리 겹침 |
| 위치 | 화면 중앙 / 가장자리(왜곡 영역) |
| 설치 | Top-view / 사선, 천장 높이별 |

### 7-4. 운영 신뢰도 임계값 정하기

Ultralytics의 기본 conf(0.25)나 mAP 최고점이 카운트 오차 최소점과 같지 않습니다. **val셋에서 conf를 0.1~0.6까지 0.05 간격으로 바꿔 가며 Count MAE와 재실 미검출률을 그리고**, 재실 미검출률 목표를 만족하는 범위에서 MAE가 가장 낮은 값을 고릅니다. 이 값을 `config.py`의 `conf_threshold`(현재 0.40)에 반영합니다. test셋은 이 과정에 쓰지 않습니다.

후처리 설계안 D2(저신뢰 검출 연계)를 적용하면 낮은 conf 검출을 버리지 않고 기존 트랙 유지에만 쓰므로, conf를 조금 높게 잡아도 착석자 미검출을 막을 수 있습니다.

### 7-5. 카운트 평가 스크립트 (요지)

```python
from pathlib import Path
from ultralytics import YOLO
import numpy as np

model = YOLO("runs/occucool/stage2_full/weights/best.pt")
img_dir = Path("/path/to/occucool_dataset/images/test")
lbl_dir = Path("/path/to/occucool_dataset/labels/test")

errs, empty_fp, occ_fn = [], [], []
for img in sorted(img_dir.glob("*.jpg")):
    lbl = lbl_dir / f"{img.stem}.txt"
    gt = sum(1 for l in lbl.read_text().splitlines() if l.startswith("0 ")) if lbl.exists() else 0
    r = model.predict(img, imgsz=416, conf=0.35, classes=[0], device="mps", verbose=False)[0]
    pred = len(r.boxes)
    errs.append(pred - gt)
    if gt == 0: empty_fp.append(pred > 0)
    else:       occ_fn.append(pred == 0)

e = np.abs(np.array(errs))
print(f"MAE={e.mean():.3f}  ±1={np.mean(e <= 1):.3%}  exact={np.mean(e == 0):.3%}")
print(f"공실 오검출률={np.mean(empty_fp):.3%}  재실 미검출률={np.mean(occ_fn):.3%}")
```

조건별 평가는 이미지 파일명이나 별도 메타데이터 CSV(공간, 조명, 자세, 가림)로 묶어 같은 계산을 반복합니다.

### 7-6. INT8 변환과 실기기 검증

```python
model = YOLO("runs/occucool/stage2_full/weights/best.pt")
model.export(format="tflite", int8=True, imgsz=416, data="data/occucool.yaml")  # val 이미지로 보정
model.export(format="tflite", int8=True, imgsz=320, data="data/occucool.yaml")
```

- 보정(calibration) 데이터에 **야간 IR과 0명 이미지가 들어가 있는지** 확인합니다. 빠지면 그 조건에서 INT8 정확도가 크게 떨어집니다.
- 변환한 `.tflite`를 i.MX 8M Plus의 NPU 델리게이트로 실행해 **7-2의 지표를 같은 test셋으로 다시 계산**합니다. PC에서 잰 FP32 점수로 합격 판정을 하지 않습니다.
- 320과 416 중 **지연 200ms 이하를 만족하는 가장 정확한 쪽**을 배포 해상도로 정하고, `vision.py`의 `UltralyticsDetector(imgsz=640)` 기본값을 그 값으로 바꿉니다.
- 24시간 연속 실행으로 발열에 따른 지연 변화를 확인합니다.

## 8. 실험 계획 (한 번에 하나만 바꾸기)

| ID | 실험 | 바꾸는 것 | 판단 기준 | 장비 |
|---|---|---|---|---|
| **E0** | NPU 호환성 사전 점검 | YOLO11n / YOLOv8n / YOLO26n 구조를 INT8로 내보내 실기기 실행 | NPU 실행 비율, 지연 | i.MX 8M Plus |
| E1 | 제로샷 기준선 | COCO `yolo11n.pt`의 `person` 클래스만으로 test 평가 | 미세조정이 얼마나 개선하는지 보는 기준점 | 맥북 |
| E2 | 모델 크기 | YOLO11n vs YOLO11s (같은 설정) | n이 MAE 0.1명 이내로 따라오면 n 확정 | 클라우드 GPU 권장 |
| E3 | 학습 방식 | 2단계 vs 처음부터 전체 미세조정 | 2단계가 같거나 좋으면 2단계 유지 | 맥북 |
| E4 | 프리징 범위 | `freeze` 11 / 6 / 0 (1단계) | 2단계 최종 MAE | 맥북 |
| E5 | 해상도 | 학습·배포 320 vs 416 | 가장자리 머리 재현율, 실기기 지연 | 맥북 + 실기기 |
| E6 | 증강 | `scale` 0.3/0.5/0.6, `flipud` 0/0.5, `multi_scale` 켜기 | 조건별 MAE | 맥북 (`fraction=0.5`로 단축) |
| E7 | 클래스 구성 | head 단독 vs head+person | 카운트 MAE, 구역 할당 정확도 | 맥북 |
| E8 | INT8 | per-channel vs per-tensor, 보정 데이터 구성 | INT8 하락폭 | 맥북 + 실기기 |

E0을 가장 먼저 하는 이유는 **학습을 다 마친 뒤 NPU에서 안 돌아간다는 것을 알게 되는 상황**을 막기 위해서입니다.

## 9. 일정과 Go/No-Go 기준

### 9-1. 진행 순서 (가정)

| 주차 | 작업 | 산출물 |
|---|---|---|
| 1 | E0 NPU 점검, 개발 환경 구성, 공개 데이터 준비·라벨 변환 | 모델 구조 확정 |
| 2~3 | 자체 데이터 수집 (동의 세션), 라벨 기준 확정, 라벨링 | train/val/test 분할 |
| 4 | E1 기준선, 1·2단계 학습 | 첫 번째 `best.pt` |
| 5 | E3~E7 실험, 조건별 약점 분석, 데이터 보강 | 최종 학습 설정 |
| 6 | INT8 변환(E8), 실기기 검증, 임계값 결정 | 배포용 `.tflite` |
| 7~ | 파이프라인 L2 검증 → 파일럿 L3 검증 | PRD 판정 자료 |

### 9-2. 단계별 통과 기준

| 관문 | 통과 조건 | 실패 시 |
|---|---|---|
| G1 모델 선택 | E0에서 INT8 지연 100ms 이하, NPU에서 거의 전부 실행 | YOLOv8n으로 교체 |
| G2 모델 성능 (test, FP32) | MAE ≤ 0.5, ±1 ≥ 95%, 재실 미검출률 ≤ 0.5%, **모든 조건 칸에서** ±1 ≥ 90% | 약한 조건 데이터 보강 후 2단계 재학습 |
| G3 양자화 (실기기, INT8) | G2 조건을 그대로 만족, 지연 ≤ 200ms | 8장 E8 시도, 해상도 조정 |
| G4 파이프라인 | 연속 영상에서 확정 인원 ±1 ≥ 95%, 변화 감지 5초 이내 | 추적·필터 파라미터 조정 (후처리 설계안) |
| G5 파일럿 | 재실 중 절전 오작동 구역당 월 1건 이하 (3~5개소) | 현장 데이터로 [3]단계 재학습 |

G5까지 통과해야 PRD의 "조건부 Go" 조건(인원 계수 정확도 95% 이상)을 충족한 것으로 봅니다.

## 10. 추가 확인이 필요한 항목

1. **공개 데이터셋 라이선스**: CrowdHuman, SCUT-HEAD, CEPDOF·HABBOF·WEPDTOF의 상업적 사용 가능 여부. 불가하면 학습에서 빼고 자체 데이터를 늘려야 합니다.
2. **학습용 영상 수집 동의 절차**: 현장 조사표 10-1에서 "학습용 데이터 수집 동의 가능"이 체크되지 않았습니다. 수집 세션을 따로 운영할 수 있는지 확인해야 합니다.
3. **i.MX 8M Plus NPU의 연산 지원 목록**: YOLO11 어텐션 블록과 YOLO26의 새 연산이 지원되는지 NXP eIQ 문서와 실기기로 확인해야 합니다 (E0).
4. **렌즈 사양 불일치**: PRD는 FOV 110~130° 광각, 현장 조사표는 일반 화각(~90°)입니다. 렌즈에 따라 가장자리 왜곡과 머리 크기가 달라지므로 학습 데이터 촬영 전에 확정해야 합니다.
5. **IR 카메라 확보**: 야간 IR 실측 이미지가 test셋에 반드시 필요합니다.
6. **11~15명 장면**: 고밀도 장면은 연출이 어렵습니다. 회의·수업 시간에 맞춰 수집 일정을 잡아야 합니다.
7. **사선 설치 비중**: 전처리 설계안에서 사선 설치가 필요하다고 봤으므로, 그 비중에 따라 `flipud` 값과 별도 모델 필요 여부가 달라집니다.
