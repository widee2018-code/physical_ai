# OccuCool 후처리 설계안

검토 자료: `PRD/PRD_AI.md`(제품 요구사항), `report/preprocess_report.md`(현장 맞춤 전처리 설계안), `code/occucool_pipeline`(전처리·제어 파이프라인 구현 코드)

## 0. 요약

전처리 설계안과 현재 코드는 **입력 신호를 깨끗하게 만드는 일**은 충실히 하고 있습니다. 예를 들면 검출 박스 필터(V4), 추적(V5), 중앙값·Hampel(V7), 비대칭 Debounce(V9), 출력 보호(P1)가 있습니다. 하지만 서비스로 운영하려면 다음 네 가지가 비어 있습니다.

1. **"0명"이라는 출력을 믿어도 되는지 확인하는 단계가 없습니다.** 렌즈가 가려지거나, 앉아 있는 사람의 신뢰도가 떨어지면 그대로 공실이 되고 에어컨이 꺼집니다.
2. **PRD가 약속한 제어 출력과 응답 시간을 맞추지 못합니다.** 풍량 제어, 인원 4구간, 감지 후 5초 이내 명령, 시간당 설정 변경 4회 이하 조건이 이에 해당합니다.
3. **판단 결과를 서비스로 전달하는 단계가 없습니다.** 알림 중복 억제, 오프라인 버퍼링, 외부 전송 데이터 검사가 빠져 있습니다.
4. **파일럿 Go/No-Go를 판정할 지표를 자동으로 계산하지 않습니다.** 지금은 에너지 기준선(E2)만 있습니다.

이 설계안은 이 공백을 메우는 **후처리 14단계**를 제안합니다. 그중 파일럿 전에 반드시 넣어야 할 것은 D1(영상 건전성), D2(저신뢰 검출 연계), C1(공실 확정 게이트), G1(설정 변경 빈도 제한), N2(오프라인 버퍼링), L1(외부 전송 검사) 6개입니다.

> 이 문서에서 '후처리'는 **모델 추론 결과가 나온 뒤부터 데이터가 서버에 도착하기까지** 거치는 모든 단계를 뜻합니다. 검출 결과 정제, 재실 판정 검증, 제어 출력 변환, 명령 확인, 알림, 로그·리포트가 여기에 들어갑니다.

## 2. 후처리 파이프라인

### 2-1. 전체 흐름

굵은 글씨가 이번에 추가하는 단계이고, 나머지는 기존 단계입니다.

```
[검출 계층]
V3 검출 ─→ **D1 영상 건전성 판정** ─→ V4 박스 필터
           (프레임 폐기 전 마지막 지점)    ├ **D3 설치 방식별 기하 필터**
                                          ├ **D4 정적 오검출 억제 맵**
                                          └ **D5 타일 경계 중복 병합**
        ─→ **D2 저신뢰 검출 2단계 연계** ─→ V5 추적 ─→ V6 투영·구역 ─→ V7·V8

[재실 계층]
V9 상태 머신 ─→ **C1 공실 확정 게이트** ─→ M1·M2(+D1 플래그) ─→ M3

[제어 계층]
규칙 판단 ─→ **K1 인원 구간 → 설정온도·풍량 매핑** ─→ **K2 이벤트 기반 즉시 제어**
        ─→ P1 출력 보호 + **G1 설정 변경 빈도 제한** ─→ 명령 전송 ─→ A2 확인

[서비스 계층]
이벤트 ─→ **N1 알림 정규화·중복 억제** ─→ **L1 외부 전송 검사** ─→ **N2 오프라인 버퍼링** ─→ MQTT
서버   ─→ **L2 KPI 산출** ─→ **L3 절전 오작동 의심 구간 추출** ─→ **L4 월간 리포트·파라미터 제안**
```

## 3. 단계별 기능과 근거

### [검출 계층]

#### D1. 영상 건전성 판정 (V3와 V4 사이, 신규 · 1차 필수)

**기능**
프레임을 폐기하기 직전에 프레임 하나당 스칼라 4개만 계산합니다.
- 평균 밝기: 너무 어둡거나 포화된 프레임
- 선명도(라플라시안 분산): 렌즈 오염·초점 이탈
- 이전 프레임과의 차이: 화면 정지(카메라 드라이버 멈춤)
- 기준 배경과의 구조 차이: 카메라가 돌아갔거나 무언가가 렌즈를 가림

이 값이 N초 이상 기준을 벗어나면 `camera_degraded` 플래그를 내보냅니다. M2 안전 모드 판정(`fusion.py:36`)에는 `camera_blocked` 같은 이유로 들어갑니다.

**근거**
- 지금 `camera_fault`는 프레임 결측이 5분을 넘을 때만 켜집니다. 렌즈가 가려지면 프레임은 정상으로 들어오고 검출기가 **"0명"을 정상 값으로** 내보냅니다. 그러면 5분 뒤 공실이 확정되고 Setback 후 OFF로 갑니다.
- 결과는 전처리 보고서의 **위험 1위(거짓 공실)**와 같은데, 기존 대응책(유령 유지, 결측의 재실 해석)으로는 막을 수 없습니다. 결측이 아니라 '정상처럼 보이는 0'이기 때문입니다.
- PRD는 "카메라 가림" 알림과 "카메라 이상 시 직전 설정 유지 + 운영 스케줄 전환"을 명시합니다. 이 판정이 없으면 그 요구사항을 실행할 트리거가 없습니다.
- **반드시 V4 앞에 와야 합니다.** 픽셀을 볼 수 있는 마지막 지점이 `del masked`(`vision.py:430`)이기 때문입니다. 계산 결과는 숫자 4개뿐이라 "영상 저장·전송 0건" 원칙도 지켜집니다.
- 조명이 일정한 현장(보고서: 창 없음, LED 상시 점등)이라 밝기 기준이 안정적입니다. 오탐 위험이 낮아 임계값을 단순하게 잡을 수 있습니다.

**초기값 (가정)**
- 밝기: 평균 < 15 또는 > 240
- 선명도: 설치 시 기준값의 30% 미만
- 정지 판정: 프레임 차이 0이 60초 지속
- 이상 유지: 30초 이상이면 플래그

#### D2. 저신뢰 검출 2단계 연계 (V4와 V5 사이, 수정 · 1차 필수)

**기능**
V4의 신뢰도 필터를 둘로 나눕니다.
- **고신뢰(≥ 0.40):** 새 트랙 생성과 기존 트랙 매칭에 모두 사용합니다.
- **저신뢰(0.15~0.40):** 1차 매칭 후 남은 **기존 확정 트랙**과의 2차 매칭에만 씁니다(ByteTrack 방식). 새 트랙은 만들지 않습니다.
- 매칭되지 않은 저신뢰 검출 중 같은 자리에 반복해서 나타나는 것은 `weak_presence` 증거로 C1에 넘깁니다.

**근거**
- PRD가 AI를 쓰는 이유로 든 것이 "착석·정지 상태, 부분 가림"입니다. 이런 자세는 신뢰도가 0.2~0.4로 떨어지기 쉽습니다.
- 지금 검출기는 conf 0.1까지 받지만(`vision.py:84`) V4가 0.4 미만을 트래커 앞에서 버립니다(`vision.py:206`). 그래서 앉아 있는 사람의 트랙이 10초 소실 버퍼 뒤에 끊깁니다. 출입구를 거치지 않았으니 유령으로 5분 남았다가 사라지고, 결국 거짓 공실이 됩니다.
- 보고서는 "이 현장은 미검출이 더 위험하므로 재현율 우선"이라고 하고, 추적기 후보로 ByteTrack을 직접 언급합니다. 임계값을 그냥 낮추면 오검출 트랙이 늘어납니다. 반면 2단계 연계는 **이미 확인된 사람의 유지에만** 저신뢰를 써서 재현율과 정밀도를 함께 지킵니다.
- 추가 연산은 매칭 한 번뿐이라 2fps·5명 이하 조건에서 부담이 없습니다.
- **V5 앞에 와야 합니다.** 매칭 후보 집합 자체를 바꾸는 단계이기 때문입니다.

#### D3. 설치 방식별 기하 필터 분기 (V4 내부, 수정 · 설치 결정 시 즉시)

**기능**
`install_mode = oblique | overhead`를 설정으로 두고 V4·V6 규칙을 나눕니다.

| 항목 | 사선 (oblique, 현재 코드) | 천장 직하·어안 (overhead) |
|---|---|---|
| 종횡비 필터 | 높이/폭 ≥ 1.2 | 끄거나 0.6~1.6 허용 |
| 위치 기준점 | 박스 하단 중앙(발) | 박스 중심(머리) |
| 최소 크기 | 고정 24px | 화면 중심에서의 거리에 따라 다르게 |

**근거**
- PRD는 "천장 설치, 광각 110~130°, 머리·상체 검출"을 기술 스택으로 정했습니다. 반면 보고서는 커버리지 계산(중앙 설치 시 시야 폭 1.4m)을 근거로 "사선 설치나 어안 렌즈가 사실상 필수"라고 결론냈습니다. 코드는 사선을 전제로 합니다(`config.py:33`, `vision.py:53`).
- 위에서 내려다본 머리·어깨 박스는 거의 1:1이라 종횡비 1.2 필터에서 **대부분 걸러집니다.** 어안 가장자리에서는 박스 하단이 실제 위치와 크게 어긋나 구역 할당도 틀어집니다.
- 설치 방식이 확정되지 않은 상태(보고서 7장 3-1/3-3 항목)에서 한쪽만 하드코딩하면, 어느 쪽으로 결정되든 절반의 현장에서 계수가 무너집니다. 분기로 두면 설치 결정과 코드 수정이 분리됩니다.

#### D4. 정적 오검출 억제 맵 (V4 내부, 신규 · 2차)

**기능**
비운영 시간(O2 = `closed`)에 움직임 없이 반복 검출되는 위치를 바닥 격자(예: 0.5m)에 누적합니다. 누적이 기준을 넘은 칸은 그 위치의 신뢰도 임계값을 올립니다(예: +0.2). 아예 차단하지는 않으며, 운영 시간에 그 칸에서 이동하는 트랙이 확인되면 점수를 천천히 낮춥니다.

**근거**
- 의자에 걸린 외투, 포스터, 모니터 화면 속 사람이 1명으로 잡히면 **공실이 영원히 확정되지 않습니다.** 절감 효과는 "공실 정확 판정 → OFF/Setback"에서 대부분 나오므로(보고서 판단 2), 거짓 재실은 절감률을 직접 깎습니다. PRD 목표는 15%이고, 회수기간 24개월을 맞추려면 최소 7%가 필요합니다.
- 정적 ROI 마스크는 설치 시점의 고정 영역만 막고, 나중에 놓인 물체에는 대응하지 못합니다.
- 보고서 7장은 "무인 상태 사진은 허위 검출 확인용 배경 기준"이라며 확보를 권하지만, 영상을 저장할 수 없습니다. 이 맵은 **좌표 통계만으로** 같은 역할을 합니다.
- 완전히 마스크하지 않고 임계값만 올리는 이유가 있습니다. 실제로 그 자리에 앉는 사람을 영구적으로 못 보는 위험(거짓 공실)을 피하기 위해서입니다.

#### D5. 타일 경계 중복 병합 (V4 NMS 직후, 신규 · 원거리 타일 사용 시)

**기능**
전체 프레임 박스와 타일 박스를 합칠 때 IoU 대신 **IoS(작은 박스 기준 겹침 비율) ≥ 0.6**이면 같은 사람으로 보고 병합합니다.

**근거**
- 보고서는 사선 설치 시 원거리 타일링을 필수로 둡니다. 타일 경계에 걸린 사람은 잘린 작은 박스와 전체 박스로 두 번 검출되는데, 둘의 IoU는 0.5 미만인 경우가 많아 표준 NMS로는 지워지지 않습니다.
- 5명 이하 현장에서 1명 중복은 단계 판정(1~2명 → 3명 이상)을 바로 뒤집습니다. PRD의 MAE 0.5명 목표에도 직접 영향을 줍니다.

### [재실 계층]

#### C1. 공실 확정 게이트 (V9 직후, 신규 · 1차 필수)

**기능**
V9가 OCCUPIED → VACANT 전환을 내리려 할 때, 아래 조건을 **모두** 만족해야 전환을 승인합니다. 하나라도 걸리면 공실 타이머를 보류합니다.
1. D1이 지난 공실 확정 구간 동안 영상 정상으로 판정했습니다.
2. D2의 `weak_presence` 증거가 최근 2분간 없습니다.
3. 유령(ghost)이 남아 있지 않습니다.
4. 마지막 확정 트랙이 출입구 근처에서 사라졌습니다. 아니라면 공실 확정 시간을 1.5배로 늘립니다.

승인·보류 사유는 모두 이벤트 로그에 남깁니다.

**근거**
- PRD 신뢰성 지표 중 가장 엄격한 것이 "재실 중 절전 오작동 구역당 월 1건 이하"입니다. 공실 판정은 **되돌리기 비싼 판단**입니다. 압축기 재기동 보호 때문에 다시 켜는 데 최소 5분이 걸리고, 그동안 재실자 불만이 생깁니다. 그래서 들어가는 쪽(입실)보다 나가는 쪽(공실)에 검증을 더 두는 비대칭 설계가 맞습니다. 보고서의 비대칭 Debounce와 같은 논리입니다.
- 지금 V9는 `count == 0`이 5분 지속됐는지만 봅니다(`occupancy.py:188`). D1·D2의 증거를 받을 자리가 없습니다. 게이트를 별도 단계로 두면 상태 머신은 단순하게 유지하면서 증거를 모을 수 있습니다.
- PRD의 "퇴장 후 절전: 유예 10분 + 5초 이내"와도 충돌하지 않습니다. 정상 퇴실(출입구 통과, 증거 없음)은 기본 시간에 그대로 승인되기 때문입니다.

### [제어 계층]

#### K1. 인원 구간 → 설정온도·풍량 매핑 (규칙 판단 직후, 수정 · 2차)

**기능**
현장 프로필별 구간표를 설정으로 둡니다.

| 프로필 | 구간 | 출력 |
|---|---|---|
| PRD 기본(150㎡, 최대 15명) | 0 / 1~5 / 6~10 / 11+ | 절전 / 기본 / −1℃·풍량 중 / −2℃·풍량 강 |
| 파일럿(보고서, 최대 5명) | 0 / 1~2 / 3~5 | 절전 / 기본 / −1℃·풍량 중 |

`HVACState.fan`을 실제로 채우고, 풍량 피드백이 없는 기종에서는 확인 대상에서 제외합니다. `matches`(`hvac.py`)는 이미 `fan`이 None이면 비교를 건너뜁니다.

**근거**
- PRD의 핵심 가치인 "인원수로 설정온도와 **풍량**을 정량적으로 조정"이 코드에 없습니다(`control.py:70`은 설정온도만 바꿉니다).
- 풍량은 설정온도보다 실내에서 체감 반응이 빠릅니다. 인원이 급증했을 때 풍량을 먼저 올리면, 압축기 부하를 크게 바꾸지 않고도 PRD의 쾌적도 유지율 90%를 맞추기 쉽습니다.
- 보고서는 5명 이하 현장에서 인체 발열(0.5kW)이 작으므로 단계를 3개로 줄이라고 했고, PRD는 4구간을 정했습니다. 둘은 **현장 규모가 다를 뿐** 모순이 아닙니다. 그래서 하드코딩하지 않고 프로필로 분리합니다.

#### K2. 이벤트 기반 즉시 제어 (M3와 병렬, 신규 · 2차)

**기능**
1분 정기 주기와 별개로, 다음 이벤트가 생기면 해당 10초 그리드에서 바로 제어 판단을 실행합니다.
- VACANT → OCCUPIED 전환
- 재실 단계 상승
- 안전 모드 진입

**쾌적 방향만** 즉시 실행합니다. 절전 방향(단계 하락, 공실)은 정기 주기를 그대로 따릅니다.

**근거**
- PRD 응답 시간 지표는 "인원 변화 감지 5초 이내, 감지 후 제어 명령 5초 이내"입니다. 지금은 1분 주기 대기만으로도 최대 60초가 걸립니다(`pipeline.py:183`).
- 보고서는 "카세트 응답 지연이 수 분 단위이므로 1분 주기면 충분"하다고 했습니다. 이는 **온도 도달** 관점에서는 맞지만, PRD는 이 지표를 "실내온도 도달 시간과 별개"로 명시했습니다. 사용자가 체감하는 것은 "들어왔는데 에어컨이 반응하는가"입니다.
- 쾌적 방향만 즉시 처리하는 이유는 보고서 위험 2위(단주기 운전)를 피하기 위해서입니다. 켜는 쪽은 빠르게, 끄는 쪽은 느리게 하는 비대칭은 V9·C1과 같은 원칙입니다.
- 입실 Debounce 30초(`config.py:58`)는 문 앞을 지나는 사람을 거르는 장치라 유지합니다. 대신 출입구를 통과해 **안쪽 구역에 자리 잡은 트랙**은 Debounce를 10초로 줄이는 예외를 둘 수 있습니다.

#### G1. 설정 변경 빈도 제한 (P1 내부, 수정 · 1차 필수)

**기능**
`ControlGuard`에 두 개의 카운터를 추가합니다.
1. 마지막 설정 변경 후 5분 이내 재변경 금지
2. 최근 60분 동안 4회 초과 금지

예외는 두 가지입니다.
- OFF → ON(재실 복귀)과 안전 모드 진입은 제한하지 않습니다.
- 제한에 걸린 명령은 버리지 않고 **최신 목표 하나만 보류**했다가 허용 시점에 보냅니다.

**근거**
- PRD 신뢰성 지표는 "설정 변경 시간당 4회 이하"이고, 시나리오는 "설정 변경은 최소 5분 간격"입니다. 지금 변화율 제한은 불쾌 방향(냉방 중 온도 상승)에만 걸립니다(`control.py:132`). 쾌적 방향은 1분마다 바뀔 수 있습니다.
- K2가 즉시 제어를 추가하므로 G1은 **K2와 반드시 함께** 들어가야 합니다. 응답성을 높이는 장치와 진동을 막는 장치가 짝을 이룹니다.
- 최신 목표만 보류하는 이유가 있습니다. 중간 명령을 모두 쌓으면 허용 시점에 오래된 목표가 연달아 나가 오히려 진동이 생깁니다.

#### (기존 유지) A2 명령 확인

추가 기능은 없고, 파라미터만 정리합니다.

| 항목 | PRD | 보고서 | 코드 |
|---|---|---|---|
| 재시도 횟수 | 3회 | 최대 2회 | `max_retries=2`(`config.py:96`) |
| 수동 조작 보류 | 2시간 | 60분 | 3600초(`config.py:97`) |

어느 값을 따를지 결정해야 합니다. 확인 결과(`confirmed`, `retry`, `alarm`)는 L2의 제어 성공률 계산 입력이 됩니다.

### [서비스 계층]

#### N1. 알림 정규화·중복 억제 (이벤트 직후, 신규 · 2차)

**기능**
- 흩어진 이벤트(`alarm`, `energy_mismatch`, `manual_override`, `camera_degraded`, `temp_invalid`, 오프라인)를 하나의 스키마 `{type, severity, zone, started_at, resolved_at, count}`로 정규화합니다.
- **같은 유형은 열린 상태 하나로 묶습니다.** 반복 발생하면 count만 올립니다.
- 해소되면 '해제' 알림을 한 번 보냅니다.
- 심각도별로 채널을 다르게 씁니다.
  - 긴급(제어 실패, 카메라 가림): 푸시
  - 주의(센서 보간 지속): 일일 요약
  - 정보(수동 조작): 대시보드만

**근거**
- PRD는 제어 실패·센서·카메라·오프라인 알림을 FCM/이메일/Slack으로 보내고, 담당자가 알림을 받아 현장을 점검하는 흐름을 정의합니다. 지금은 `log.info` 한 줄뿐입니다(`pipeline.py:144`).
- 중복 억제가 없으면 Wi-Fi가 자주 끊기는 현장(보고서 7장 5-5: 신호 불안정도 미확인)에서 알림이 수십 건 쏟아집니다. 담당자가 알림을 끄게 되고, 정작 중요한 제어 실패를 놓칩니다.
- 해제 알림은 "점검하러 가야 하는가"를 판단하는 데 필요합니다. 그래서 현장 출동 비용(PRD ROI의 유지보수 월 150만 원)과 직접 연결됩니다.
- 수동 조작을 '정보'로 분류하되 집계는 남깁니다. PRD 지표인 "수동 조작 50% 감소"를 측정하는 원천이기 때문입니다.

#### L1. 외부 전송 검사 (전송 직전, 신규 · 1차 필수)

**기능**
기기 밖으로 나가는 모든 메시지를 **허용 목록 스키마**로 검사합니다.
- 허용 필드: 숫자·열거형·타임스탬프(인원수, 구역별 카운트, 온습도, 상태, 이벤트)
- 차단 조건: 바이트 배열·base64·임의 길이 문자열, 정해진 크기 초과
- 차단한 메시지는 내용 없이 '차단 건수'만 기록합니다.

**근거**
- PRD 프라이버시 지표는 "영상 외부 전송·저장 0건, 트래픽 감사로 측정"입니다. 지금 코드는 **입력 쪽**(프레임 폐기)으로 이를 보장하지만, 디버깅 코드나 향후 기능 추가로 박스 이미지·썸네일이 로그에 섞여 나가는 것을 **출력 쪽**에서 막는 장치는 없습니다.
- 입력과 출력 양쪽에 검사를 두면 트래픽 감사의 근거가 "그렇게 만들었다"에서 "구조적으로 나갈 수 없다"로 바뀝니다. 파일럿 기관(공공시설·학교)의 개인정보 검토를 통과하는 데 결정적입니다.
- **N2보다 앞서야 합니다.** 검사 전 데이터를 디스크 버퍼에 쓰면, 그 자체가 기기 내 저장이 됩니다.

#### N2. 오프라인 버퍼링·재전송 (L1 직후, 신규 · 1차 필수)

**기능**
- 검사를 통과한 메시지에 일련번호를 붙여 기기 내 링 버퍼(디스크, 예: SQLite WAL)에 먼저 기록하고 그다음 MQTT로 보냅니다.
- 서버 ACK를 받은 번호까지 정리합니다.
- 네트워크 복구 시 미전송분을 순서대로 다시 보냅니다. 서버는 일련번호로 중복을 제거합니다.
- S3의 사후 보간값(`backfill` 이벤트)도 같은 경로로 보냅니다.

**근거**
- PRD 신뢰성 지표는 "네트워크 단절 24시간 이상 로컬 제어 유지, **복구 후 로그 누락 0건**"입니다. 로컬 제어는 이미 기기 안에서 돌지만, 로그는 `sink` 콜백으로 흘러가 사라집니다(`pipeline.py:93`).
- 로그 누락은 단순한 데이터 손실이 아닙니다. 에너지 절감률(E2)과 KPI(L2)를 그 구간에서 계산할 수 없게 되고, 파일럿 Go 판정의 신뢰도가 떨어집니다.
- 용량 산정: 10초 그리드 레코드 약 200B × 8,640/일 ≈ 1.7MB/일입니다. 24시간 버퍼는 수 MB 수준이라 엣지 저장장치에 부담이 없습니다.

#### L2. KPI 산출 (서버, 신규 · 2차)

**기능**
10초 그리드 로그와 이벤트 로그로 PRD 지표를 매일 자동 계산합니다.

| 지표 | 계산 | PRD 목표 |
|---|---|---|
| 쾌적도 유지율 | 재실 구간 중 \|실내온도 − 설정온도\| ≤ 1.5℃ 시간 비율 | ≥ 90% |
| 시간당 설정 변경 | 시간별 설정 변경 횟수의 최댓값 | ≤ 4회 |
| 압축기 재기동 위반 | E1 압축기 OFF → ON 간격 < 3분 건수 | 0건 |
| 제어 성공률 | `confirmed` / 전송 명령 수 | ≥ 99% |
| 감지 → 명령 지연 | 상태 전환 이벤트 → 명령 전송 시각 차의 95백분위 | ≤ 5초 |
| 퇴장 후 절전 | 마지막 퇴장 → 절전 명령 시각 차 | ≤ 10분 + 5초 |
| 수동 조작 빈도 | `manual_override` 일별 건수, 도입 전 대비 | 50% 감소 |
| 에너지 절감률 | E2 기준선 대비 | ≥ 15% (파일럿 ≥ 10%) |

보간·추정 플래그가 붙은 구간은 분모에서 빼고, 제외 비율을 함께 표시합니다.

**근거**
- PRD의 최종 판정은 "**조건부 Go**: 파일럿에서 실측 절감률 10% 이상, 인원 계수 정확도 95% 이상 검증"입니다. 지금은 절감률만 계산할 수 있습니다.
- 지표를 사람이 매번 로그를 열어 계산하면 3~5개소 파일럿에서 비교 기준이 흔들립니다. 같은 코드로 매일 계산해야 현장 간 비교가 공정합니다.
- 품질 플래그 기반 제외는 보고서 4장의 권고("보간·추정 구간을 가중치 감소나 제외 처리")를 지표 계산에 그대로 적용한 것입니다.

#### L3. 절전 오작동 의심 구간 추출 (서버, 신규 · 2차)

**기능**
다음 패턴을 '절전 오작동 의심'으로 자동 표시합니다.
- 공실 확정 후 N분(예: 10분) 안에 재입실
- 절전 후 수동으로 다시 켬
- C1 보류가 반복됨

의심 구간의 시각, 구역, 당시 카운트·신뢰도 통계를 목록으로 만듭니다.

**근거**
- PRD 지표 "재실 중 절전 오작동 월 1건 이하"는 측정 방법을 "이벤트 로그와 현장 확인"으로 정했습니다. 모든 공실 전환을 현장에서 확인할 수는 없으므로 **확인할 후보를 좁혀 주는 단계**가 필요합니다.
- 영상을 저장하지 않으므로 오검출 사례를 사후에 볼 수 없습니다. 의심 시각 목록이 있어야 다음 현장 방문 때 그 시간대에 수기 라벨링(PRD: 테스트셋 1,000장 이상)을 집중할 수 있습니다. 이 목록은 PRD의 "분기별 수동 재학습"을 위한 데이터 수집 계획의 입력이 됩니다.

#### L4. 월간 리포트·파라미터 제안 (서버, 신규 · 3차)

**기능**
L2·L3 결과에 다음을 더해 월간 리포트를 만듭니다.
- 부재 시간 분포: 공실이 몇 분 만에 끝났는지의 히스토그램
- 수동 조작 시 사용자가 고른 설정온도의 분포

이를 근거로 파라미터 조정을 **제안만** 합니다. 예: "공실의 30%가 7분 안에 끝남 → 공실 확정 5분을 8분으로 늘릴 것을 권장". 적용은 담당자가 승인합니다.

**근거**
- PRD 시나리오의 마지막 단계는 "월간 리포트를 보고 유예시간과 기본 온도를 조정"입니다. 그런데 리포트에 **조정 근거**가 없으면 담당자는 감으로 바꿉니다.
- 보고서 3장 파라미터는 모두 "초기 추정치이며 현장 로그로 반드시 튜닝"하라고 되어 있습니다. 공실 확정 지연의 조정 기준은 "잠깐 자리를 비운 경우까지 꺼지면 늘린다"입니다. 부재 시간 분포는 이 기준을 그대로 수치화한 것입니다.
- 수동 조작은 보고서에서 "사용자 선호 데이터로 분리 저장"하라고 한 항목입니다. 그 분포는 기본 설정온도(PRD 26℃, 코드 24℃) 결정에 바로 쓸 수 있습니다.
- 자동 적용하지 않는 이유가 있습니다. v1은 규칙 기반 제어이고 클라우드 자동 학습은 범위 밖이기 때문입니다(PRD 5장).

## 4. 순서가 바뀌면 안 되는 이유

- **D1은 V4보다 앞서야 합니다.** V4 이후에는 영상이 폐기되므로 픽셀 기반 판정을 할 수 없습니다. 반대로 V4 뒤로 미루려면 프레임을 더 오래 들고 있어야 하므로 원본 미저장 원칙과 충돌합니다.
- **D3·D4는 V4의 신뢰도 필터 단계 안에서, D5는 NMS 직후에 와야 합니다.** 기하 필터와 위치별 임계값은 박스가 트래커에 들어가기 전에 확정돼야 합니다. 타일 병합은 NMS가 지우지 못한 잔여 중복만 다뤄야 연산이 적습니다.
- **D2는 V5보다 앞서야 합니다.** 저신뢰 검출을 매칭 후보에 넣는 것은 추적의 입력을 바꾸는 일입니다. 추적이 끝난 뒤에는 이미 끊긴 트랙을 되살릴 수 없습니다.
- **C1은 V9 직후, M1보다 앞서야 합니다.** 공실 판정이 통합 레코드(M1)에 기록된 뒤 뒤집히면 로그와 제어가 서로 다른 상태를 갖게 됩니다.
- **K1 → K2 → G1 순서여야 합니다.** 무엇을 보낼지(K1), 언제 보낼지(K2)가 정해진 다음에 보호(G1)가 걸려야 합니다. G1이 앞에 있으면 K2의 즉시 명령이 보호를 우회합니다.
- **L1은 N2보다 앞서야 합니다.** 검사하지 않은 데이터를 디스크에 쓰는 것 자체가 기기 내 저장입니다.
- **L2·L3·L4는 서버에서 해야 합니다.** 여러 현장을 같은 코드로 계산해야 비교가 공정하고, 엣지 기기의 연산·저장 부담도 줄일 수 있습니다.

## 5. 도입 순서 제안

**1차 (파일럿 설치 전, 필수)**
- D1, D2, C1: 거짓 공실을 세 겹으로 막습니다. "재실 중 절전 오작동 월 1건"을 맞추기 위한 최소 구성입니다.
- G1: 시간당 변경 4회 지표 위반을 구조적으로 막습니다.
- L1, N2: 프라이버시 0건과 로그 누락 0건은 **측정 자체가 Go 조건**이라, 파일럿 첫날부터 있어야 합니다.
- D3: 설치 방식(사선/천장)이 결정되는 즉시 넣습니다.

**2차 (그림자 모드 1~2주 동안)**
- K1, K2: 그림자 모드는 명령을 보내지 않으므로, 매핑과 즉시 제어의 판단을 실제 운전 기록과 비교하며 안전하게 검증할 수 있습니다.
- N1, L2, L3: 그림자 모드 기간의 로그로 알림 기준과 KPI 계산을 먼저 맞춰 둡니다.
- D4: 비운영 시간 데이터가 1~2주 쌓여야 맵이 의미를 가집니다.

**3차 (파일럿 1개월 이후)**
- L4: 최소 한 달치 분포가 있어야 제안이 안정적입니다.
- D5: 원거리 타일을 실제로 쓰는 현장에서만 넣습니다.

## 7. 결정이 필요한 불일치 항목

후처리 설계와 별개로, 세 문서가 서로 다른 값을 가지고 있어 결정이 필요합니다. 후처리 단계의 기본값도 이 결정에 따라 달라집니다.

| 항목 | PRD | 전처리 보고서 | 코드 | 영향 받는 후처리 |
|---|---|---|---|---|
| 카메라 설치 | 천장, 광각 110~130° | 사선 또는 어안 권장 | 사선 전제 | D3 |
| 추론 속도 | 5fps 이상 | 재실 2fps / 공실 0.5fps | 2fps(`config.py:23`) | D2, K2 |
| 인원 구간 | 0 / 1~5 / 6~10 / 11+ | 0 / 1~2 / 3~5 | 단계 기준 (1, 3)(`config.py:60`) | K1 |
| 냉방 기본 설정온도 | 26℃ | 미정 | 24℃(`config.py:105`) | K1, L4 |
| 공실 처리 | 유예 10분 후 절전 | 공실 확정 5분 + Setback → OFF | 5분 + Setback 30분 → OFF | C1, L2 |
| 압축기 재기동 간격 | 3분 | 최소 ON/OFF 5분 | 5분(`config.py:112`) | G1, L2 |
| 명령 재시도 | 3회 | 최대 2회 | 2회 | A2, L2 |
| 수동 조작 우선 | 2시간 | 60분 | 60분 | L2 |

권장 원칙은 이렇습니다. **현장 조건에서 나온 값(보고서)을 파일럿 기본값으로 쓰고, PRD 값은 제품 기본 프로필로 둡니다.** 두 값은 K1처럼 프로필로 분리하면 공존할 수 있습니다. 다만 PRD의 측정 지표(5초, 4회, 3분, 99%)는 서비스 약속이므로 L2의 판정 기준으로는 PRD 값을 씁니다.

## 8. 범위 밖

다음은 이번 후처리 설계에 넣지 않았습니다.
- **개인 식별·재식별(Re-ID)·행동 분석:** PRD 개발 제외 범위입니다. D2·D4는 좌표와 신뢰도만 쓰고 외형 특징을 쓰지 않습니다.
- **열부하 예측 기반 선제 제어:** 인원 × 발열량 + dT/dt로 설정온도를 미리 조정하는 기능입니다. PRD가 v2 검토 항목으로 둔 예측 제어에 해당하며, L2·L4로 쌓인 데이터가 그 입력이 됩니다.
- **클라우드 자동 학습·자동 파라미터 적용:** PRD 범위 밖이며, L4는 제안까지만 합니다.
